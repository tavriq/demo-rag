# RAG по Трудовому кодексу РФ

Сервис для вопросов о трудовом праве: находит нужные статьи Трудового кодекса, отвечает по их тексту и показывает, из какой статьи взят ответ. Та же схема подходит для базы регламентов или HR-FAQ компании: поиск по своим документам, ответ со ссылками на источник, измеренное качество поиска и потолок расходов на модель.

Что здесь сделано: корпус из 534 статей, гибридный поиск, ответ модели с цитатами, защита бюджета от перерасхода, прогон метрик на отложенной части вопросов, Docker-контейнер примерно на 300 МиБ памяти.

**Статус на 2026-10-05.** Демо работает на сервере в режиме без ключа API: поиск настоящий, вместо ответа модели показаны найденные фрагменты. Публичного адреса пока нет, контейнер слушает только localhost. Модель ещё ни разу не отвечала, поэтому скриншота живого ответа и метрик ответов нет: для этого нужен ключ.

## Как попробовать

Docker (порт только на localhost):

```bash
docker compose -p demo-rag up -d --build          # первый старт строит индекс, около 2,5 минуты
curl -s 127.0.0.1:18101/api/health
curl -s -X POST 127.0.0.1:18101/api/ask -H 'Content-Type: application/json' \
     -d '{"question": "Как оплачивается работа в выходной день?"}'
```

Страница с вопросами — `http://127.0.0.1:18101/`, метрики — `/evals`. Без Docker — раздел «Запуск локально» ниже.

## Коротко

- **Поиск.** Гибрид BM25 и `multilingual-e5-small` (int8 ONNX), слияние через RRF с весами 1 : 1,5. Hit@5 — 81,4% на 43 вопросах, на отложенной части (test) — 81,0%. Прогон 2026-10-05 на сервере демо, файл [`evals/latest.md`](evals/latest.md).
- **Гибрид здесь проигрывает своей же части.** На том же сервере dense без BM25 даёт hit@5 90,7%. Переключаться на него по тем же вопросам, на которых он измерен, значит подгонять под тест: решать на новом отложенном наборе.
- **Что реально видит модель.** Ей уходят 5 фрагментов. Нужная статья среди них в 76,7% вопросов. Для вопросов, где нужны две статьи, обе попадают к модели в 1 из 9.
- **Ответы модели не прогонялись: нужен ключ.** Точность цитат, отказы, стоимость и латентность ответа не измерены.
- **Cost guard.** $1.00 в сутки с точностью до цента, не больше 20 платных ответов в час на всех, 10 вопросов в час с одного адреса (IPv4 или сеть IPv6 /64). Повторный вопрос отвечается из кэша бесплатно. Тело запроса до 16 КБ, вопрос обрезается до 500 символов, ответ до 600 токенов.
- **Подбор настроек** шёл только на dev-части вопросов. Протокол, все итерации и разбор промахов — в [`evals/tuning.md`](evals/tuning.md).
- **Контейнер** занимает 288–312 МиБ при лимите 700 МиБ, файловая система только для чтения, слушает только localhost.

## Задача

Сотрудник или кадровик спрашивает разговорным языком, а не словами закона. Например: «Опоздал на работу почти на пять часов подряд. Это уже считается прогулом?». В ст. 81 это сказано так: «отсутствия на рабочем месте без уважительных причин более четырех часов подряд». Формулировки разные, общих слов мало, но гибрид ставит ст. 81 первой. А для вопроса «Женюсь в следующем месяце. Сколько дней за свой счёт мне обязаны дать?» нужную ст. 128 он не находит даже в top-5. Это известный промах, он есть в списке на `/evals` и разобран в `evals/tuning.md`.

Системе нужно:

1. найти нужную статью среди 534, даже если вопрос задан не словами закона;
2. ответить только по тексту статьи и показать, откуда взят ответ;
3. честно сказать «в базе нет ответа», если вопрос не про кодекс (ставка НДФЛ, ипотека);
4. не дать публичной странице потратить на модель больше заданной суммы.

## Решение

- **Корпус.** ТК РФ в редакции от 25.05.2026, постатейно с consultant.ru. Сверен с официальным текстом pravo.gov.ru: у 519 из 532 общих статей совпадение пословно не ниже 0,97, остальные расхождения разобраны вручную в [`data/SOURCE.md`](data/SOURCE.md). Сверка была разовой, её скрипт в репозиторий не вошёл.
- **Фрагменты.** Статья режется на части до 350 символов. Каждая часть несёт заголовок «Статья N. Название (часть i из n)», поэтому одиночный фрагмент всегда говорит, откуда он. Всего 3200 фрагментов.
- **Поиск.** BM25 со стеммингом Snowball для русского языка и dense-поиск на e5-small, слияние Reciprocal Rank Fusion с весами 1 : 1,5. Векторной БД нет: numpy и JSON, полный перебор матрицы 3200 × 384.
- **Эмбеддинги без тяжёлых зависимостей.** Свой раннер на onnxruntime и SentencePiece вместо fastembed и HF `tokenizers`. Один только JSON-токенайзер HF увеличивал память процесса на 386 МБ, а весь сервер с SentencePiece занимает в контейнере 288–312 МиБ. По разовому замеру эмбеддинги совпадают со стандартной реализацией: косинус не ниже 0,9992. Замеры — в [`docs/design.md`](docs/design.md).
- **Ответ.** `claude-haiku-4-5-20251001`, `temperature=0`. Модель получает только найденные фрагменты. Ей велено отвечать только по ним, ставить `[ст. N]` у каждого утверждения и отвечать «В базе нет ответа на этот вопрос.», если ответа во фрагментах нет. На живой модели это пока не проверялось. Цитаты в интерфейсе — ссылки на фрагменты.
- **Без ключа.** Демо-режим: поиск настоящий, вместо ответа модели показаны найденные фрагменты с пометкой «демо-режим без ключа».

## Архитектура

```
 браузер ── POST /api/ask ──► FastAPI, один процесс uvicorn
                                  │
                  тело > 16 КБ ──► 413;  вопрос обрезается до 500 символов
                                  │
                  cost guard (SQLite) ── лимит в час на IPv4 или IPv6 /64 ──► 429
                                  │      кэш: тот же вопрос ──► готовый ответ, $0
                                  │      20 платных ответов в час на всех ──► отказ «попробуйте позже»
                                  │      резерв худшей стоимости ──► отказ «бюджет на сегодня исчерпан»
                                  ▼
              ┌──────────────── поиск ────────────────┐
              │ BM25, стемминг         e5-small int8  │
              │ top-30 фрагментов      top-30 (косинус)│
              └────────── RRF, веса 1 : 1,5 ──────────┘
                                  │ top-5 фрагментов
                                  ▼
              Claude Haiku 4.5 (без ключа — заглушка)
              <fragments>…</fragments>  <user_question>…</user_question>
                                  │ usage из ответа → фактический расход в SQLite, ответ → кэш
                                  ▼
              ответ с [ст. N] → ссылки на фрагменты; фрагменты со score

 офлайн:
   data/corpus.jsonl ─► app.build_index ─► var/index/ (meta.json, chunks.json, embeddings.npy)
   data/evals.jsonl  ─► app.evals ─► evals/runs/*.json, evals/latest.{json,md} ─► страница /evals
```

## Метрики

Прогон 2026-10-05 на сервере демо (Linux x86_64, Python 3.12, onnxruntime 1.30.0): [`evals/latest.md`](evals/latest.md), полный файл с рангами по каждому вопросу — [`evals/runs/2026-10-05T083535Z-all-linux-x86-64.json`](evals/runs/2026-10-05T083535Z-all-linux-x86-64.json). Набор — 50 вопросов: 34 с ответом в одной статье, 9 с ответом в двух статьях и 7 без ответа в кодексе. Вопросы без ответа в hit@k не входят. Статья засчитывается по лучшему из своих фрагментов, hit@5 — нужная статья среди первых пяти разных статей.

| Поиск, 43 вопроса | hit@1 | hit@3 | hit@5 | MRR@10 |
|---|---|---|---|---|
| BM25 | 32,6% | 51,2% | 58,1% | 0,425 |
| Dense (e5-small) | 69,8% | 86,0% | 90,7% | 0,766 |
| **Гибрид, работает в демо** | 55,8% | 79,1% | 81,4% | 0,673 |

| Гибрид по частям набора | n | hit@1 | hit@3 | hit@5 | MRR@10 |
|---|---|---|---|---|---|
| dev (на нём подбирались настройки) | 22 | 40,9% | 77,3% | 81,8% | 0,575 |
| test (отложен) | 21 | 71,4% | 81,0% | 81,0% | 0,775 |

Что реально получает модель. Таблица выше мягче: hit@5 считает пять разных статей, а модель получает пять фрагментов, в среднем из 3,5 статьи. Вопрос на две статьи в таблице засчитан, если найдена любая из них.

| Гибрид, тот же прогон | Значение |
|---|---|
| нужная статья среди 5 фрагментов для модели (43 вопроса) | 76,7% |
| вопросы на две статьи (9): хотя бы одна в top-5 статей | 66,7% |
| вопросы на две статьи: обе в top-5 статей | 22,2% |
| вопросы на две статьи: обе среди фрагментов для модели | 11,1% |

**Ответы модели: не прогонялось, нужен ключ.** Точность цитат, корректные отказы на вопросах без ответа, стоимость и латентность ответа не измерены. Код для этого готов: `python3 -m app.evals --answers`.

Что стоит знать о цифрах:

- **Подбор.** Три итерации на dev: фрагменты 1200 → 350 символов, в индекс идёт заголовок без названия главы, веса RRF 1 : 1,5. На test hit@5 не изменился (81,0% → 81,0%), hit@1 вырос с 57,1% до 71,4%, MRR — с 0,677 до 0,775. Файлами подтверждены только цифры после подбора: прогоны базы и итераций тогда не сохранялись. Теперь каждый прогон пишется в `evals/runs/`.
- **Dev и test неравные.** Dev получился заметно труднее: в базе hit@5 на dev 63,6%, на test 81,0%. У test мало запаса для роста, поэтому «на test hit@5 не изменился» слабо говорит о пользе подбора. Подробно, с оценкой вероятности такого перекоса, — в `evals/tuning.md`.
- **Цель не достигнута.** Для гибрида целью был hit@5 ≥ 85%, получилось 81,4%.
- **BM25 и номера статей.** BM25 оставлен ради запросов вида «статья 186.1». Точечная проверка на сервере это не подтвердила: BM25 ставит нужную статью 1-й или 2-й во всех шести таких запросах, а гибрид не находит ст. 186.1 и ст. 84.1 даже в top-10. При весах 1 : 1,5 фрагмент, который нашёл только BM25, всегда оказывается ниже всех 30 кандидатов dense. Разбор — в `evals/tuning.md`.
- **Примеры на странице.** Кнопки-примеры, подсказка в поле и пример `curl` выше выбраны так, чтобы гибрид ставил нужную статью первой. Это проверяется в каждом прогоне (раздел «Точечные проверки» в `latest.md`) и тестом на локальном индексе.
- **Платформа влияет на цифры.** Модель квантована в int8, и на разных CPU эмбеддинги немного различаются. На Mac (arm64) тот же набор даёт гибрид 83,7%, dense 86,0% ([`evals/runs/2026-10-05T080854Z-all-darwin-arm64.json`](evals/runs/2026-10-05T080854Z-all-darwin-arm64.json)). Поэтому в каждом отчёте записана платформа.
- **Набор маленький.** 43 вопроса: один вопрос — это 2,3 п. п. Вопросы составлены для этого проекта, независимой разметки не было. Каждая ожидаемая статья проверена чтением. `python3 data/check_evals.py` проверяет, что вопросы не списаны со статей (самый длинный общий кусок — 3 слова подряд) и что на вопросы без ответа в корпусе действительно нет ответа ([`data/README.md`](data/README.md)).

## Cost guard

- **Дневной лимит.** `DAILY_BUDGET_USD`, по умолчанию $1.00, сутки по UTC, учёт в SQLite. Перед вызовом модели резервируется худшая стоимость: 5 фрагментов максимальной длины, вопрос, системный промпт и полные 600 токенов ответа по ценам Haiku 4.5 ($1 за 1M входных и $5 за 1M выходных токенов). Это до $0.0075 на вопрос при 5 фрагментах и до $0.0090 при 8 (API принимает `top_k` до 8). Проверка и резерв идут в одной транзакции, поэтому параллельные запросы не проскочат лимит вместе. После ответа резерв заменяется фактом из `usage`.
- **Точность лимита — до цента.** Оценка входа исходит из 2 символов на токен, и на живом API это не проверено. Вопрос из эмодзи или иероглифов может стоить больше резерва. Перерасход ограничен запросами, которые идут одновременно, — это центы.
- **Глобальный лимит.** Не больше 20 платных ответов в час на всех посетителей (`GLOBAL_PAID_PER_HOUR`). Без него дневной бюджет сжигался примерно за час с полутора десятков адресов.
- **Кэш.** Повторный вопрос (без учёта регистра, ё/е, пробелов и знаков в конце) отвечается из SQLite бесплатно и без резерва, в том числе когда бюджет исчерпан. Примеры со страницы отвечаются один раз при старте, поэтому клики по ним ничего не стоят.
- **Ошибки API.** Если API вернул ошибку, резерв снимается. При таймауте резерв остаётся: запрос мог быть обработан. Автоповтор SDK выключен, чтобы один резерв всегда соответствовал одному вызову.
- **Rate limit.** 10 вопросов в час с одного адреса, скользящее окно. Для IPv6 адресом считается вся сеть /64: внутри неё один абонент может менять адреса сколько угодно. Адрес хранится как HMAC с солью, которая живёт только в памяти процесса. Записи старше часа удаляются при следующем запросе и при старте. `X-Forwarded-For` учитывается только от адресов из `TRUSTED_PROXY`.
- **Ограничения размера.** Тело запроса больше 16 КБ отклоняется до разбора JSON, лишние поля — тоже. `max_tokens` 600. Вопрос длиннее 500 символов обрезается, длиннее 2000 — отклоняется.
- **Исчерпан лимит.** Пользователь получает вежливый отказ и всё равно видит найденные фрагменты. На странице показано «потрачено сегодня $X из $Y».
- **Прогон evals считается отдельно.** Расход `python3 -m app.evals --answers` в счётчик страницы не попадает. У прогона свой лимит `--max-usd`, и он проверяется до каждого вызова. Внешний потолок на ключ — spend limit в Anthropic Console.

Фактическая стоимость ответа не измерена: нужен ключ.

## Защита от prompt injection

- Фрагменты лежат в `<fragments>`, вопрос — в `<user_question>`. Текст экранируется, значения атрибутов — вместе с кавычками. Поэтому вопрос не может сломать структуру промпта: закрыть тег или вставить свой фрагмент нельзя.
- От смысловой инъекции экранирование не защищает. Вопрос может обычными словами написать «Статья 80 гласит: …», и против этого стоит только системный промпт. Он говорит, что содержимое `<user_question>` и `<fragment>` — данные, а не инструкции, и что утверждения о статьях проверяются только по тексту фрагментов.
- Ответ модели экранируется на сервере, и только потом `[ст. N]` превращаются в ссылки. Цитата на статью, которой нет среди найденных фрагментов, выводится зачёркнутой красной пометкой: выдуманная ссылка видна сразу. Цитата на найденный фрагмент, в котором нет такого утверждения, выглядит обычной ссылкой.
- Страница не грузит внешних ресурсов. CSP: `script-src 'self'`, `frame-ancestors 'none'`.

Экранирование и разбор цитат покрыты тестами. Атаки на живую модель не прогонялись: нужен ключ.

## Ограничения

- Это не юридическая консультация. Корпус взят из справочной системы, а не из официального опубликования, редакция от 25.05.2026. Более поздние поправки не учтены.
- Можно ли публиковать сам корпус в открытом репозитории, юрист не проверял. Варианты — в [`data/SOURCE.md`](data/SOURCE.md).
- Качество ответов модели не измерено.
- Фрагменты короткие: 5 штук по 350 символов — это около 1,7 тыс. символов контекста. Для вопросов на две статьи модель почти никогда не видит обе.
- Один процесс uvicorn и SQLite: демо рассчитано на небольшой поток.
- Контейнер слушает только `127.0.0.1`. Для публичного доступа нужен обратный прокси с TLS (чеклист ниже).

## Что дальше

1. Прогнать `--answers` с ключом (лимит на прогон `--max-usd 0.50`), опубликовать точность цитат, отказы, стоимость и латентность и положить сюда скриншот живого ответа с цитатами. Заодно сравнить `usage.input_tokens` с оценкой на вопросах из эмодзи и иероглифов.
2. Расширить набор до 150–200 вопросов с независимой разметкой. Вопросы и разбиение закоммитить отдельным коммитом до первого прогона.
3. На новом отложенном наборе решить: оставлять ли BM25 и с каким весом, нужен ли отдельный поиск по номеру статьи, убирать ли повторы одной статьи во фрагментах или поднять TOP_K до 8.
4. Добавить в набор вопросы-инъекции и прогнать их через `--answers`.
5. Замерить память с реранкером (cross-encoder): помещается ли он в лимит 700 МиБ.

## Запуск локально

Нужен Python 3.12.

```bash
python3 -m venv .venv && . .venv/bin/activate
pip install -r requirements-dev.txt
python3 -m pytest                                          # 120 тестов, без сети и ключа (тест на настоящем индексе — после build_index)
python3 -m app.build_index --corpus data/corpus.jsonl      # при первом запуске скачает модель (~125 МБ)
uvicorn --factory app.main:create_app --port 8000 --no-proxy-headers
```

Без `ANTHROPIC_API_KEY` приложение работает в демо-режиме. Чтобы включить ответы модели, задайте ключ перед запуском: `export ANTHROPIC_API_KEY=...`.

Evals:

```bash
python3 -m app.evals --evals data/evals.jsonl              # только поиск, без LLM
python3 -m app.evals --evals data/evals.jsonl --split dev  # только dev-часть, для подбора настроек
python3 -m app.evals --evals data/evals.jsonl --answers    # плюс ответы модели, нужен ключ, лимит --max-usd 0.50
python3 data/check_evals.py                                # проверки набора вопросов против корпуса
```

Каждый прогон сохраняется в `evals/runs/`. `evals/latest.*` (их показывает `/evals`) переписывает только полный прогон: весь набор, без `--limit` и `--split`. Если прогонять `--answers`, то последним: следующий прогон без ключа перезапишет `latest.*` уже без ответов.

docker compose -p demo-rag up -d --build

Как устроен контейнер:

- образ `python:3.12-slim` закреплён по digest, зависимости ставятся из `requirements.lock` с хэшами (`--require-hashes`);
- процесс работает от непривилегированного пользователя, `cap_drop: ALL`, `no-new-privileges`, файловая система только для чтения, `/tmp` в памяти, `pids_limit: 128`, `mem_limit: 700m`;
- индекс, кеш модели и SQLite с учётом расходов и кэшем ответов лежат в volume;
- индекс строится при первом старте и пересобирается, когда меняется корпус или версия индекса. На 2 vCPU это около 2,5 минуты вместе со скачиванием модели;
- порт — только `127.0.0.1:18101`.

## Перед публикацией

Сейчас демо наружу не открыто. Если открывать:

- `TRUSTED_PROXY` — адрес прокси или подсеть docker-шлюза (`docker network inspect demo-rag_default`). Иначе все посетители придут с одного адреса и попадут в один лимит; `/api/health` тогда показывает `proxy_headers_ignored: true`.
- На прокси — лимит тела запроса 16 КБ и TLS.
- В Anthropic Console — spend limit на ключ или workspace как внешняя страховка.
- Ключ — в `.env` с правами 600.
- Ответ юриста про публикацию корпуса ([`data/SOURCE.md`](data/SOURCE.md)).

## Настройки

| Переменная | По умолчанию | Что делает |
|---|---|---|
| `ANTHROPIC_API_KEY` | — | без ключа — демо-режим |
| `DAILY_BUDGET_USD` | `1.00` | дневной лимит расходов на модель, сутки по UTC |
| `GLOBAL_PAID_PER_HOUR` | `20` | платных ответов в час на всех посетителей |
| `RATE_LIMIT_PER_HOUR` | `10` | вопросов в час с одного адреса (IPv4 или IPv6 /64) |
| `WARM_CACHE` | `1` | при старте с ключом ответить на примеры со страницы и положить в кэш |
| `MAX_TOKENS` | `600` | предел длины ответа |
| `MAX_QUESTION_CHARS` | `500` | более длинный вопрос обрезается |
| `TOP_K` | `5` | сколько фрагментов уходит в модель |
| `CHUNK_MAX_CHARS` | `350` | размер фрагмента (подобран на dev) |
| `BM25_WEIGHT` / `DENSE_WEIGHT` | `1.0` / `1.5` | веса RRF (подобраны на dev) |
| `TRUSTED_PROXY` | пусто | IP или CIDR прокси, которым можно верить в `X-Forwarded-For` |

Полный список — в `.env.example` и `app/config.py`.
