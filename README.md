# RAG по Трудовому кодексу РФ

Сервис для вопросов о трудовом праве: находит нужные статьи Трудового кодекса, отвечает по их тексту и показывает, из какой статьи взят ответ. Та же схема подходит для базы регламентов или HR-FAQ компании: поиск по своим документам, ответ со ссылками на источник, измеренное качество и потолок расходов на модель.

Что здесь сделано: корпус из 534 статей, поиск по смыслу, ответ языковой модели со ссылками на статьи, лимиты расходов, замер качества на отложенной части вопросов, Docker-контейнер примерно на 260 МиБ памяти.

**Статус на 2026-10-05.** Демо работает на сервере с живой моделью `openai/gpt-5.6-terra` через шлюз Timeweb AI. Это OpenAI-совместимый API, подойдёт и любой другой такой. Живое демо: https://rag.tavriq.ru, до 10 вопросов в час с одного адреса. Снаружи сервис закрыт nginx с TLS, сам контейнер слушает только localhost. Без ключа API приложение работает в демо-режиме: поиск настоящий, а вместо ответа модели показан список найденных статей.

## Как попробовать

Docker, порт только на localhost:

```bash
docker compose -p demo-rag up -d --build          # первый старт строит индекс, около 2,5 минуты
curl -s 127.0.0.1:18101/api/health
curl -s -X POST 127.0.0.1:18101/api/ask -H 'Content-Type: application/json' \
     -d '{"question": "Как оплачивается работа в выходной день?"}'
```

Страница с вопросами — `http://127.0.0.1:18101/`, метрики — `/evals`. Без ключа ответит демо-режим. Как подключить модель — в разделе «Свой ключ API». Без Docker — раздел «Запуск локально».

Живой ответ на этот вопрос (сервер демо, 2026-10-05, 953 токена на входе, 138 на выходе, 2,4 с вместе с поиском):

> Работа в выходной день оплачивается не менее чем в двойном размере; для сдельщиков — не менее чем по двойным сдельным расценкам, для работников с дневными или часовыми тарифными ставками — не менее двойной ставки. [ст. 153] Конкретные размеры оплаты могут устанавливаться коллективным договором, локальным нормативным актом или трудовым договором. [ст. 153] По желанию работника может предоставляться другой день отдыха: тогда работа оплачивается в одинарном размере, а день отдыха не оплачивается. [ст. 153]
> Это не юридическая консультация.

На странице `[ст. 153]` — ссылка на фрагмент статьи, из которого взято утверждение.

## Термины

- **Фрагмент** — кусок статьи до 350 символов с заголовком «Статья N. Название». Поиск и модель работают с фрагментами, а не с целыми статьями.
- **Поиск по смыслу** (dense, эмбеддинги) — текст переводится в вектор чисел моделью `multilingual-e5-small`, близкие по смыслу тексты дают близкие векторы. Находит статью, даже если в вопросе нет её слов.
- **Поиск по словам** (BM25) — классический поиск по совпадению слов с учётом их редкости.
- **Гибрид** (RRF) — слияние двух списков выдачи в один. В демо выключен: по замерам поиск по смыслу без него точнее.
- **Роутер номеров статей** — правило: если в вопросе есть «ст. 81» или «статья 186.1», фрагменты этой статьи ставятся первыми.
- **hit@5** — доля вопросов, где нужная статья среди первых пяти найденных. **MRR** — то же с учётом места: 1 за первое место, 0,5 за второе и так далее, среднее по вопросам.
- **Evals** — автоматический прогон набора вопросов с известными ответами и подсчёт метрик.
- **dev и test** — две половины набора вопросов. Настройки выбираются только по dev. Test смотрится в конце, это честная оценка на вопросах, под которые ничего не подгонялось.
- **Токен** — единица текста, в которой модели считают объём и цену. На живом прогоне промпт на русском давал около 3,6 символа на токен.
- **Демо-режим** (mock) — работа без ключа API: поиск настоящий, модель не вызывается.

## Задача

Сотрудник или кадровик спрашивает разговорным языком, а не словами закона. Например: «Опоздал на работу почти на пять часов подряд. Это уже считается прогулом?». В ст. 81 это сказано так: «отсутствия на рабочем месте без уважительных причин более четырех часов подряд». Формулировки разные, общих слов мало, но поиск по смыслу ставит ст. 81 первой. А для вопроса «Женюсь в следующем месяце. Сколько дней за свой счёт мне обязаны дать?» нужную ст. 128 он не находит даже среди первых пяти. Это известный промах, он есть в списке на `/evals` и разобран в `evals/tuning.md`.

Системе нужно:

1. найти нужную статью среди 534, даже если вопрос задан не словами закона;
2. ответить только по тексту статьи и показать, откуда взят ответ;
3. честно сказать «в базе нет ответа», если вопрос не про кодекс;
4. не дать публичной странице потратить на модель больше заданного лимита.

## Решение

- **Корпус.** ТК РФ в редакции от 25.05.2026, постатейно с consultant.ru. Сверен с официальным текстом pravo.gov.ru: у 519 из 532 общих статей совпадение пословно не ниже 0,97, остальные расхождения разобраны вручную в [`data/SOURCE.md`](data/SOURCE.md). Сверка была разовой, её скрипт в репозиторий не вошёл.
- **Фрагменты.** Статья режется на части до 350 символов. Каждая часть несёт заголовок «Статья N. Название (часть i из n)», поэтому одиночный фрагмент всегда говорит, откуда он. Всего 3200 фрагментов.
- **Поиск.** По смыслу, модель `multilingual-e5-small` (квантованная int8, формат ONNX). Векторной базы данных нет: numpy и JSON, полный перебор матрицы 3200 × 384 занимает доли миллисекунды. Номер статьи в вопросе перехватывает роутер: регулярное выражение на «ст.», «статья», «статьи» и номер вида 81, 186.1 или 341.1-1. Поиск по словам (BM25) и гибрид остались в коде, в каждом прогоне метрик и включаются настройкой `SEARCH_MODE`.
- **Почему без гибрида.** Сначала демо работало на гибриде. На сервере поиск по смыслу оказался точнее, а гибрид не находил запросы по номеру статьи. Выбор сделан по dev-половине вопросов по правилу, записанному до прогона, и только потом проверен на test. Протокол и цифры — в [`evals/tuning.md`](evals/tuning.md), итерация 4.
- **Эмбеддинги без тяжёлых зависимостей.** Свой раннер на onnxruntime и SentencePiece вместо fastembed и токенайзера Hugging Face: один только JSON-токенайзер HF добавлял процессу 386 МБ. Эмбеддинги совпадают со стандартной реализацией (косинус не ниже 0,9992 по разовому замеру). Замеры — в [`docs/design.md`](docs/design.md).
- **Ответ.** Любая модель за OpenAI-совместимым API (`POST /chat/completions`). На сервере демо — `openai/gpt-5.6-terra` через шлюз Timeweb AI, temperature 0, ответ до 600 токенов. Модель получает только 5 найденных фрагментов. Ей велено отвечать только по ним, ставить `[ст. N]` у каждого утверждения и отвечать «В базе нет ответа на этот вопрос.», если ответа во фрагментах нет. Ссылки в ответе превращаются в ссылки на фрагменты.
- **Без ключа.** Демо-режим: поиск настоящий, вместо ответа модели показаны найденные статьи с пометкой «демо-режим без ключа».

## Метрики

Прогон 2026-10-05 на сервере демо (Linux x86_64, Python 3.12, onnxruntime 1.30.0): [`evals/latest.md`](evals/latest.md). Набор — 50 вопросов: 34 с ответом в одной статье, 9 с ответом в двух статьях и 7 без ответа в кодексе. Вопросы без ответа в метрики поиска не входят. Статья засчитывается по лучшему из своих фрагментов.

**Поиск, 43 вопроса.** Все три способа на одном прогоне. Демо работает на первом.

| Поиск | hit@1 | hit@3 | hit@5 | MRR@10 |
|---|---|---|---|---|
| **По смыслу (dense), работает в демо** | 69,8% | 86,0% | 90,7% | 0,766 |
| Гибрид, веса 1 : 1,5 (было в демо до 2026-10-05) | 55,8% | 79,1% | 81,4% | 0,673 |
| По словам (BM25) | 32,6% | 51,2% | 58,1% | 0,425 |

| Поиск по смыслу по половинам набора | n | hit@1 | hit@3 | hit@5 | MRR@10 |
|---|---|---|---|---|---|
| dev (по ней выбирались настройки) | 22 | 68,2% | 81,8% | 86,4% | 0,739 |
| test (отложена) | 21 | 71,4% | 90,5% | 95,2% | 0,795 |

**Что реально видит модель.** hit@5 считает пять разных статей, а модель получает пять фрагментов, в среднем из 3,5 статьи. Нужная статья среди них в 88,4% вопросов (у гибрида было 76,7%). Для 9 вопросов на две статьи обе доходят до модели только в 1 случае. Это главное слабое место.

**Ответы модели, 50 вопросов** (`openai/gpt-5.6-terra`, шлюз Timeweb AI):

| Метрика | Значение |
|---|---|
| ответ ссылается на ожидаемую статью (43 вопроса с ответом) | 79,1% |
| ответ «в базе нет ответа», хотя в кодексе он есть | 23,3% (10 из 43) |
| честный отказ на 7 вопросах не про кодекс | 7 из 7 |
| ответы без единой ссылки (отказы не считаются) | 0 из 33 |
| все ссылки ведут на фрагменты, которые модель получила | 100% |
| ответ оборван лимитом длины | 0 |
| время ответа модели: медиана / 95-й процентиль / среднее | 1,57 с / 4,00 с / 1,78 с |
| токенов на ответ: вход / выход / из них на рассуждения | 918 / 57 / 6 |
| весь прогон | 48 759 токенов |

Почему 10 отказов. В 5 вопросах нужной статьи нет среди фрагментов: это промах поиска, и отказ здесь правильный. В 2 статья найдена, но пришла не та её часть. В 1 вопросе на две статьи модель ответила по найденной и честно отказала по второй. В 2 модель отказала, хотя часть ответа во фрагментах была. Разбор по каждому вопросу — в [`evals/tuning.md`](evals/tuning.md). Сравнительный прогон на второй модели шлюза (`gpt-5.6-luna`) не делался: другая модель не увидит фрагменты, которые до неё не дошли.

Что стоит знать о цифрах:

- **«Ссылается на нужную статью» не значит «ответ верный».** Автоматической проверки содержания нет. Я прочитал все 33 ответа, где модель не отказала, и сверил с эталонными подсказками из набора: противоречий не нашёл, неполнота есть. Например, в ответе про возраст приёма на работу нет общего правила «с 16 лет». Это ручная проверка одним человеком.
- **Test здесь не слепой.** Результат поиска по смыслу на test можно было вычислить из прошлого прогона ещё до выбора. Правило выбора записано до прогона, решение закоммичено до проверки на test, но независимой эту проверку назвать нельзя. Подробно — в `evals/tuning.md`.
- **Платформа влияет на цифры.** Модель эмбеддингов квантована в int8, и на разных процессорах ранги немного различаются. Поэтому официальные цифры сняты на сервере, где работает демо, а в каждом отчёте записана платформа.
- **Набор маленький.** 43 вопроса: один вопрос — это 2,3 п. п. Каждая ожидаемая статья проверена чтением. `python3 data/check_evals.py` проверяет, что вопросы не списаны со статей (самый длинный общий кусок — 3 слова подряд) и что на вопросы без ответа в корпусе ответа действительно нет ([`data/README.md`](data/README.md)).
- **Примеры на странице** и пример `curl` выше выбраны так, чтобы поиск ставил нужную статью первой. Это проверяется в каждом прогоне (раздел «Точечные проверки» в `latest.md`) и тестом на локальном индексе.

## Лимиты расходов

Цены шлюза проекту неизвестны, поэтому лимиты считаются в токенах, а не в деньгах. Выдумывать цену нельзя: выдуманная цена дала бы выдуманный лимит.

- **Дневной лимит.** `DAILY_TOKEN_BUDGET`, по умолчанию 300 000 токенов в сутки по UTC на всех посетителей, учёт в SQLite. Это около 300 ответов при фактических ~975 токенах на ответ.
- **Часовой лимит на всех.** `HOURLY_TOKEN_BUDGET`, по умолчанию 50 000 токенов за последний час. Без него дневной лимит можно сжечь за час с полутора десятков адресов.
- **Резерв до вызова модели.** Перед вызовом резервируется худший случай: 5 самых длинных фрагментов, вопрос в 500 символов, системный промпт из расчёта 2 символа на токен плюс все 600 токенов ответа. Это до 4 097 токенов при 5 фрагментах и до 5 612 при 8 (API принимает `top_k` до 8). Проверка и резерв идут в одной транзакции, поэтому параллельные запросы не проскочат лимит вместе. После ответа резерв заменяется фактом из `usage`. На живом прогоне фактический вход не превысил 0,57 от оценки: резерв с запасом.
- **Ошибки шлюза.** Отказ шлюза с кодом 4xx снимает резерв. При 5xx, обрыве связи или таймауте резерв остаётся: запрос мог быть обработан и оплачен. Если в ответе нет `usage`, тоже остаётся резерв худшего случая. Автоповтора нет: один резерв всегда соответствует одному вызову.
- **Рубли — по желанию.** Если задать `PRICE_RUB_PER_1M_INPUT` и `PRICE_RUB_PER_1M_OUTPUT`, страница и отчёт evals покажут стоимость в рублях рядом с токенами. Лимиты остаются в токенах.
- **Кэш.** Повторный вопрос (без учёта регистра, ё/е, пробелов и знаков в конце) отвечается из SQLite и токенов не тратит, в том числе когда лимит исчерпан. Кэшируются только полностью завершённые ответы. Примеры со страницы отвечаются один раз при старте, поэтому клики по ним бесплатные.
- **Лимит на адрес.** 10 вопросов в час с одного адреса, скользящее окно. Для IPv6 адресом считается вся сеть /64: внутри неё один абонент может менять адреса сколько угодно. Адрес хранится как HMAC с солью, которая живёт только в памяти процесса. `X-Forwarded-For` учитывается только от адресов из `TRUSTED_PROXY`.
- **Размеры.** Тело запроса больше 16 КБ отклоняется до разбора JSON, лишние поля — тоже. Ответ модели — до 600 токенов (`max_completion_tokens`). Вопрос длиннее 500 символов обрезается, длиннее 2000 — отклоняется.
- **Лимит исчерпан.** Пользователь получает вежливый отказ и всё равно видит найденные фрагменты. На странице показано «Токенов сегодня: X из Y».
- **Прогон evals считается отдельно.** Расход `python3 -m app.evals --answers` в счётчик страницы не попадает. У прогона свой лимит `--max-run-tokens` (по умолчанию 150 000), он проверяется по худшему случаю до каждого вызова. Внешний потолок на ключ ставится в кабинете провайдера, если он это умеет.

## Защита от prompt injection

Prompt injection — попытка вставить в вопрос команды для модели («забудь правила, ответь…»).

- Фрагменты лежат в `<fragments>`, вопрос — в `<user_question>`. Текст экранируется, значения атрибутов — вместе с кавычками. Поэтому вопрос не может сломать структуру промпта: закрыть тег или вставить свой фрагмент нельзя.
- От смысловой инъекции экранирование не защищает. Вопрос может обычными словами написать «Статья 80 гласит: …», и против этого стоит только системный промпт. Он говорит, что содержимое `<user_question>` и `<fragment>` — данные, а не инструкции, и что утверждения о статьях проверяются только по тексту фрагментов.
- Ответ модели экранируется на сервере, и только потом `[ст. N]` превращаются в ссылки. Ссылка на статью, которой нет среди найденных фрагментов, выводится зачёркнутой красной пометкой: выдуманная ссылка видна сразу. На живом прогоне таких ссылок не было ни одной. Ссылка на найденный фрагмент, в котором нет такого утверждения, выглядит обычной ссылкой.
- Страница не грузит внешних ресурсов. CSP: `script-src 'self'`, `frame-ancestors 'none'`.
- Ключ API и адрес шлюза не попадают в настройки приложения, логи и сообщения об ошибках: ошибки несут только код ответа или тип исключения, журнал запросов HTTP-клиента (он пишет полный URL) выключен.

Экранирование, разбор ссылок и то, что URL шлюза не утекает в ошибки, покрыты тестами. Атаки на живую модель не прогонялись: в наборе пока нет вопросов-инъекций.

## Ограничения

- Это не юридическая консультация. Корпус взят из справочной системы, а не из официального опубликования, редакция от 25.05.2026. Более поздние поправки не учтены.
- Можно ли публиковать сам корпус в открытом репозитории, юрист не проверял. Варианты — в [`data/SOURCE.md`](data/SOURCE.md).
- Фрагменты короткие: 5 штук по 350 символов — это около 1,7 тыс. символов контекста. Для вопросов на две статьи модель почти никогда не видит обе, а иногда получает не ту часть нужной статьи.
- Модель предпочитает отказ неполному ответу: в 2 вопросах она отказала, хотя часть ответа во фрагментах была.
- Один процесс uvicorn и SQLite: демо рассчитано на небольшой поток.
- Контейнер слушает только `127.0.0.1`. Для публичного доступа нужен обратный прокси с TLS (чеклист ниже).

## Что дальше

1. Отдавать модели соседние фрагменты найденной статьи или целую статью, если она короткая. Это закроет отказы, где статья найдена, но пришла не та часть. Решать на новом отложенном наборе.
2. Расширить набор до 150–200 вопросов с независимой разметкой. Вопросы и разбиение закоммитить отдельным коммитом до первого прогона.
3. Добавить вопросы-инъекции и прогнать их через `--answers`.
4. Добавить автоматическую проверку содержания ответа (сверка с эталоном), а не только ссылки на статью.
5. Замерить память с реранкером: помещается ли он в лимит 700 МиБ.

## Свой ключ API

Подходит любой OpenAI-совместимый API: приложение шлёт `POST {LLM_BASE_URL}/chat/completions` с заголовком `Authorization: Bearer <ключ>`. Нужны две переменные, без любой из них работает демо-режим. `LLM_BASE_URL` — адрес до `/chat/completions`, обычно с `/v1` на конце: у OpenAI это `https://api.openai.com/v1`, у шлюза — адрес из его документации.

```bash
install -m 600 /dev/null .env          # файл для ключа, читать может только владелец
cat >> .env <<'EOF'
LLM_API_KEY=ваш-ключ
LLM_BASE_URL=https://api.openai.com/v1
LLM_MODEL=имя-модели-у-этого-провайдера
EOF
docker compose -p demo-rag up -d       # или export этих переменных перед uvicorn при запуске без Docker
curl -s 127.0.0.1:18101/api/health     # "mode": "live" и имя модели
```

- `LLM_MODEL` по умолчанию `openai/gpt-5.6-terra` — так модель называется в шлюзе Timeweb AI. У другого провайдера имя будет своё.
- Рассуждающим моделям задайте `LLM_REASONING_EFFORT=minimal`. Без этого модель может потратить все 600 токенов на рассуждения и вернуть пустой ответ. Приложение покажет это как «Модель не успела ответить», а не как отказ.
- Если модель не принимает `temperature`, задайте `LLM_TEMPERATURE=none`, и параметр не будет отправляться.
- Ключ не коммитить: `.env` в `.gitignore`. В логи и ответы API ключ и адрес шлюза не попадают.

## Запуск локально

Нужен Python 3.12.

```bash
python3 -m venv .venv && . .venv/bin/activate
pip install -r requirements-dev.txt
python3 -m pytest                                          # 168 тестов, без сети и ключа (тест на настоящем индексе — после build_index)
python3 -m app.build_index --corpus data/corpus.jsonl      # при первом запуске скачает модель (~125 МБ)
uvicorn --factory app.main:create_app --port 8000 --no-proxy-headers
```

Без `LLM_API_KEY` и `LLM_BASE_URL` приложение работает в демо-режиме. Как включить ответы модели — в разделе «Свой ключ API».

Evals:

```bash
python3 -m app.evals --evals data/evals.jsonl              # только поиск, без модели
python3 -m app.evals --evals data/evals.jsonl --split dev  # только dev-половина, для выбора настроек
python3 -m app.evals --evals data/evals.jsonl --answers    # плюс ответы модели, лимит --max-run-tokens 150000
python3 -m app.evals --answers --no-latest                 # сравнительный прогон, latest.* не трогает
python3 data/check_evals.py                                # проверки набора вопросов против корпуса
```

Каждый прогон сохраняется в `evals/runs/`. `evals/latest.*` (их показывает `/evals`) переписывает только полный прогон: весь набор, без `--limit`, `--split` и `--no-latest`. Если прогонять `--answers`, то последним: следующий полный прогон без ключа перезапишет `latest.*` уже без ответов.

## Docker

```bash
docker compose -p demo-rag up -d --build
```

Как устроен контейнер:

- образ `python:3.12-slim` закреплён по digest, зависимости ставятся из `requirements.lock` с хэшами (`--require-hashes`);
- процесс работает от непривилегированного пользователя, `cap_drop: ALL`, `no-new-privileges`, файловая система только для чтения, `/tmp` в памяти, `pids_limit: 128`, `mem_limit: 700m`;
- индекс, кеш модели эмбеддингов и SQLite с учётом токенов и кэшем ответов лежат в volume;
- индекс строится при первом старте и пересобирается, когда меняется корпус или версия индекса. На 2 vCPU это около 2,5 минуты вместе со скачиванием модели;
- порт — только `127.0.0.1:18101`;
- ключ — в `.env` с правами 600 (раздел «Свой ключ API»).

## Перед публикацией

Сейчас демо наружу не открыто. Если открывать:

- `TRUSTED_PROXY` — адрес, с которого прокси приходит в контейнер. При порте на `127.0.0.1` хоста это шлюз docker-сети проекта: `docker network inspect demo-rag_default --format '{{(index .IPAM.Config 0).Gateway}}'`. Без этой настройки все посетители придут с одного адреса и попадут в один лимит; `/api/health` тогда показывает `proxy_headers_ignored: true`.
- За Tailscale Funnel или `tailscale serve` нужен тот же `TRUSTED_PROXY`: tailscaled подключается к `127.0.0.1:18101` как обычный процесс хоста. Funnel ставит `X-Forwarded-For` с публичным IP клиента и перезаписывает заголовок, а не дописывает, поэтому подделать цепочку клиент не может. Источник — функция `addProxyForwardedHeaders` в коде tailscale: [`ipn/ipnlocal/serve.go`, строки 1088–1096](https://github.com/tailscale/tailscale/blob/9128778b6515f32e13d92e7380044fe025f9b08e/ipn/ipnlocal/serve.go#L1088-L1096) (`Header.Set("X-Forwarded-For", c.SrcAddr.Addr().String())`; для Funnel адрес клиента приходит от ingress-узла Tailscale в заголовке `Tailscale-Ingress-Src`). Признак запроса из интернета — заголовок `Tailscale-Funnel-Request: ?1`.
- На прокси — лимит тела запроса 16 КБ и TLS.
- У провайдера модели — внешний лимит расходов на ключ, если он есть.
- Ответ юриста про публикацию корпуса ([`data/SOURCE.md`](data/SOURCE.md)).
